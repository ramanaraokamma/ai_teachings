Main lesson · Section 2

Separate proposal, validation, execution and response

A plausible call is not evidence that a tool ran.

Understand tools and APIs

A tool exposes an operation through a declared interface. An API is a way software sends requests and receives responses. A model-produced call is only a proposal: application checks decide whether the operation is allowed and its arguments valid. A successful read-only lookup supplies data; it does not authorise borrowing, booking or deleting. This lesson simulates requests on paper and makes no network calls.

Tools expose structured operations with input and output contracts. Generating a tool call is a proposal; validation and authorisation decide whether it executes.

Keep the exercise on supplied records

Begin by writing the question the procedure is intended to answer. Identify the information already supplied, the information it will produce and the information still missing.

These are constructed classroom examples; they do not require live accounts, private records or an external service. Do not treat a plausible explanation as a measured outcome.

Repair the extra-action and missing-value shortcuts

Claim to repair: The ID exists, so ignore the extra booking field and execute the request. The contract accepts exactly one input field. Reject the extra operation before invocation rather than silently rewriting its meaning. A read-only result provides data only.
