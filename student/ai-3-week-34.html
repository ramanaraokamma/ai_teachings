Understand traceable implementation

A capstone build turns the design into inspectable stages. Keep a record of the input, eligible source, parsed facts, answerability, draft, validation and displayed outcome. Start with a deterministic baseline that preserves source facts before adding generated wording. A successful build step does not prove an experiment’s result, and a procedure description does not supply measurements.

Paper simulation remains useful when labelled; actual execution needs its own observed output.

Build the assistant as a sequence of testable stages: validate request, retrieve authorised evidence, decide answerability, draft, validate and return. Avoid merging all errors into one model score.

Use supplied fictional evidence

Begin by writing the question the procedure is intended to answer. Identify the information already supplied, the information it will produce and the information still missing.

These are constructed classroom examples; they do not require live accounts, private records or an external service. Do not treat a plausible explanation as a measured outcome.

Run or trace the complete deterministic baseline

In the structured toy program, cups/days are positive integers; optional measurements are lists of nonnegative whole mL values, one per cup. Initial volumes, when supplied, must be positive whole mL and at least the corresponding losses. These deliberately narrow assumptions are not a general measurement schema. E2 produces procedure facts with unavailable losses/half status.

E3 adds 1, 2, 3 mL losses but half remains unknown without initial volumes. No program output proves the source record was reliably measured.

def build_report(record):
    # Short fictional classroom records, not arbitrary text or live measurements.
    fields = {'source_id', 'cups', 'days', 'losses_ml', 'initial_ml'}
    if type(record) is not dict or set(record) != fields:
        raise ValueError('exact record fields required')
    if type(record['source_id']) is not str or not record['source_id']:
        raise ValueError('source ID required')
    for key in ['cups', 'days']:
        if type(record[key]) is not int or record[key] < 1:
            raise ValueError('positive integer counts required')
    losses = record['losses_ml']
    initial = record['initial_ml']
    for values, minimum in [(losses, 0), (initial, 1)]:
        if values is not None:
            if type(values) is not list or len(values) != record['cups']:
                raise ValueError('one value per cup required')
            if any(type(x) is not int or x < minimum for x in values):
                raise ValueError('integer mL values outside the toy contract')
    if initial is not None and losses is None:
        raise ValueError('initial values do not supply losses')
    if initial is not None and any(x > y for x, y in zip(losses, initial)):
        raise ValueError('loss cannot exceed initial volume')
    half = None
    if losses is not None and initial is not None:
        half = all(2 * loss == start for loss, start in zip(losses, initial))
    return {'source_id': record['source_id'],
            'procedure': {'cups': record['cups'], 'days': record['days']},
            'losses_ml': losses, 'all_lost_half': half}

E2 = {'source_id': 'E2', 'cups': 3, 'days': 4,
      'losses_ml': None, 'initial_ml': None}
E3 = {'source_id': 'E3', 'cups': 3, 'days': 4,
      'losses_ml': [1, 2, 3], 'initial_ml': None}
print(build_report(E2))
print(build_report(E3))

Repair ratio and missing-as-zero shortcuts

Claim to repair: E3 gives losses 1, 2, 3 mL, so every cup lost half its water. A fraction needs the corresponding initial volume. Loss 1 mL could be half of 2 mL but not half of 10 mL. Without initial volumes, report the losses as supplied and the ratio as unresolved. Another shortcut is replacing missing measurements with 0; that fabricates an observed zero. Retain None/null or an explicit unavailable status.
