01. Rows Columns and Data Types: the case

A fictional approved book catalogue has three fields per row. Supplied facts: Schema: id is nonempty text; pages is an integer 1–300; illustrated is Boolean True or False.

Rows A={id:"B7",pages:90,illustrated:True}; B={id:"B8",pages:"90",illustrated:False}; C={id:"",pages:80,illustrated:True}.

Point to the given fact that matters most. Explain why it matters.

02. Follow the deciding steps

Column contract: Field names identify values; order is not the only guide. → Validate A: B7 is text, 90 is allowed integer, True is Boolean: valid. → Validate B: Quoted "90" is text, so pages fails the integer contract. → Validate C: Empty id fails even though its other two values have allowed types.

Point to each numbered stage and explain which recorded input it uses.

03. Follow the evidence

Follow the evidence. activity | Nonempty text | Names the session activity. minutes | Integer 0 through 60 | Duration in minutes

Read the labels and values. Explain the relationship the model shows.

04. Change one thing. Trace what follows.

Original case: Empty id fails even though its other two values have allowed types. Changed condition: Change B’s pages from "90" to integer 90 using an approved repair. Expected result: B now satisfies the declared schema.

Reason: Its id is nonempty and illustrated is Boolean; the page-type defect is removed.

Predict before checking the worked changed-case result. Name what changed and what the supplied facts allow you to conclude.

05. Connect the explanation to its limit

A schema makes row meanings and expected types explicit. The string "90" looks like a number when printed but does not meet this strict integer schema. A repair can be authorised later, but must not be assumed silently.

Missing or empty identifiers also prevent tracing an item back to its source. Limit: Schema validity does not confirm that the book really has 90 pages or that its metadata is accurate.

Explain the case, then point to a limit on the claim.
