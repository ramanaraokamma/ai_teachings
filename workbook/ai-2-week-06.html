01. Debugging Strategies: the case

A fictional shelf function should count books in complete bundles plus loose books. Supplied facts: Correct definition: shelf(bundle_count,loose) returns bundle_count*6+loose. Faulty copied body returns (bundle_count+loose)*6.

Predict tests before running.

Point to the given fact that matters most. Explain why it matters.

02. Follow the deciding steps

Expected normal test: For (2,1), correct result is 2×6+1=13. → Faulty trace: Copied code gives (2+1)×6=18. → Zero-bundle test: For (0,3), correct 3; copied code 18. → Nonrevealing test: For (2,0), both return 12; a pass does not locate every bug.

Point to each numbered stage and explain which recorded input it uses.

03. Expected outputs versus a specific bug

Expected outputs versus a specific bug. Test 1: Bundles = 2, Loose = 1, Correct = 13, Faulty = 18. Test 2: Bundles = 0, Loose = 3, Correct = 3, Faulty = 18. Test 3: Bundles = 2, Loose = 0, Correct = 12, Faulty = 12.

Read the labels and values. Explain the relationship the model shows.

04. Change one thing. Trace what follows.

Original case: For (2,0), both return 12; a pass does not locate every bug. Changed condition: Repair the body to bundle_count*6+loose. Expected result: Expected results for (2,1),(0,3),(2,0) are 13,3,12.

Reason: Only bundles are groups of six; loose books are counted individually.

Predict before checking the worked changed-case result. Name what changed and what the supplied facts allow you to conclude.

05. Connect the explanation to its limit

Test cases need not all expose the same error. Here loose books must be added after multiplying bundles. A zero-loose case cannot distinguish the two formulas because multiplying zero loose books changes nothing.

Keep expected and actual columns so an observed output does not quietly become its own expected answer.

Limit: These three tests check a specified formula and bug; they do not prove correct handling of every type or invalid request.
