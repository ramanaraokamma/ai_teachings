Learning goal and precision

Primary target: Trace a loop by testing its condition before every repetition

Teach a pretest while loop with exact whole-number arithmetic. Track the instruction pointer, current state, test result and body count separately. Use both zero-iteration and boundary-crossing cases.

The termination explanations depend on the stated update and condition; do not claim that every increasing counter terminates. Faulty loops are paper traces, stopped by the teacher once the reason for repetition is clear.

By the end, I can check a loop condition before each update and count iterations.

What to prepare

  • Use the supplied scenario, student illustrations and blank paper. For numeric work, offer counters or a calculator after learners show the setup. Fictional records are supplied; personal data and paid accounts are unnecessary.

  • A counter card, a while condition card and a separate body card with an arrow back to the condition

  • A trace sheet with current value, true or false and action columns, plus a separate iteration tally

  • Starting-value cards including 1, 6, 7 and 8, and an add 0 fault card

Main lesson · Section 2

Teach a loop with its instruction pointer and full trace

Keep tests, iterations, current values and reporting distinguishable.

Begin with the below-7 loop and its if comparison

A paper counter starts at 1. While the counter is below 7, add 2 to it. When the test is false, report the counter and stop.

The word while means test first, run the body only if true, then return to the test using the updated value. The body here is just add 2.

The counter follows 1, 3, 5, 7. At 1, 3 and 5 the condition is true, so each test is followed by one addition. At 7 the condition is false. No addition follows that final test. The loop has three iterations and reports 7.

Compare the Week 10 instruction if counter is below 7, add 2, then report. From 1 that single decision reports 3. A while loop explicitly returns to its test; an if decision does not.

Draw a pointer to the instruction being executed instead of deciding for yourself when to repeat.

Retain the final false test and repeated states

The trace has four tests but only three iterations. The false test is evidence that this run stops. A list ending at 5 would be incomplete, while a list continuing to 9 would include an addition the loop did not authorise.

Write the current value, the test result and the action on every row. Repeated values can matter: if the body does not change the state used by the test, the same true test may occur again.

Do not erase these rows simply because they look unhelpful.

Model the separate below-10 counter

A fictional paper counter advances through a display until its condition becomes false.

Start at 2. While the current counter is below 10, add 3.

Test before each addition; report when the condition is false.

The condition checks whether to do the next update; it does not constrain every resulting value to stay below 10. The final 11 is therefore allowed by this procedure.

Record both the condition and counter to distinguish a correct stop from an assumed endpoint.

Start where the first test is false

  1. Change: Start at 10 instead of 2.

  2. Prediction: The loop runs zero times and reports 10.

  3. Reason: Its first condition is already false, so no addition happens.

Explain the progress assumption

This loop stops because positive increments eventually cross the limit. Other updates can fail to make progress.

While tests before the body. If the first test is false, the body runs zero times. Do not add 2 once just because a loop is present. Starting at 7 or 8 is a useful test of this rule.

A loop that stops when the counter is no longer below 7 does not promise to finish at exactly 7. Starting at 6 produces 8. Passing the boundary is allowed by these instructions.

Always report the actual final state instead of replacing it with the threshold.

Explain the mechanism

Follow the information instead of imagining magic inside the machine.

CORE IDEA A loop repeats a useful step until a stopping condition is met.

UNDER THE HOOD For these bounded counter exercises, specify the starting value, repeated action, update and stopping test. Check that the updates eventually make the test false; otherwise a run may continue forever or repeat the wrong number of times. Other programs may use different loop designs, such as waiting for a stop signal.

Draw a fresh example with all three stages:

Every step connects a claim to observable evidence.

CASE Instead of writing draw-side and turn four times, a square algorithm can repeat those steps four times.

STEP 1 — OBSERVE starting state and repeat count

STEP 2 — TRACE run the loop body and update progress

STEP 3 — CONCLUDE finished pattern when the stop condition is met

MODEL REASONING Place only the repeated steps inside the loop, initialize the counter, update it once per pass, and stop after the required count. Trace each iteration to catch one-too-many or one-too-few errors.

DO NOT OVERCLAIM Repeat forever is not an efficient algorithm unless endless operation is truly the goal and can be stopped safely.

Selected independent question and key

Selected case: A paper countdown starts at 7. While remaining is above 1, subtract 2. When false, report and stop. Trace the run and count iterations. Repeat from 6 and from 1. Explain why the final value need not equal 1.

What happens from 7 if subtract 2 is replaced by subtract 0?

From 7: 7 true, 5 true, 3 true, 1 false; three iterations, report 1. From 6: 6 true, 4 true, 2 true, 0 false; three iterations, report 0. From 1: first test false, zero iterations, report 1. Above 1 stops at 1 or below.

Subtracting 0 from 7 leaves every test true, so that faulty run never reports.

W1 Trace every test

Start counter at 2. While counter is below 8, add 2. When false, report and stop. Record the value and result at every test, including the final false test. State the number of iterations and the reported value.

Tests: 2 true, 4 true, 6 true, 8 false. Three additions are three iterations. The loop reports 8; the fourth test does not run the body.

W2 Check the first test

Use the same below 8 loop with add 2. Make separate runs from 8 and 9. Explain how many times the body runs and what each run reports. Why would adding 2 once be an error?

Both first tests are false. Each run has zero iterations, reporting its unchanged starting value: 8 or 9. Adding 2 once would execute the body despite a false first test.

W3 Find the extra repetition

Start counter at 3. While counter is below 8, add 2. A learner writes values 3, 5, 7, 9, 11 and reports 11. Identify the first unauthorised update. Give the correct final test, reported value and iteration count.

After 7 becomes 9, the next test 9 below 8 is false. The update from 9 to 11 is unauthorised. Report 9 after three iterations, with test rows 3 true, 5 true, 7 true, 9 false.

W5 Test a proposed stopping rule

A procedure says start at 4; while counter is not equal to 9, add 2; report and stop. Write the first four values tested. Explain why the loop will not reach 9 using whole numbers.

Suggest a changed condition that would stop once the counter reaches or passes 9, and trace that repaired run.

The first four values are 4, 6, 8, 10. Adding 2 to an even number always gives another even number, so the counter cannot become the odd number 9. Change the condition to while counter is below 9.

Then 4 true, 6 true, 8 true, 10 false; three iterations and report 10.

02. Follow the deciding steps

05. Connect the explanation to its limit

The condition checks whether to do the next update; it does not constrain every resulting value to stay below 10. The final 11 is therefore allowed by this procedure.

Record both the condition and counter to distinguish a correct stop from an assumed endpoint. Limit: This loop stops because positive increments eventually cross the limit. Other updates can fail to make progress.
