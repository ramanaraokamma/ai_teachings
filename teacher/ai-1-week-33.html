Main lesson · Section 1

Prepare this connected week

Learning goal and precision

Primary target: Plan routine cases with expected results derived from the requirements

The prototype remains an explicit rule system. This lesson focuses on prewritten expectations, repeatable conditions and honest records. Q version 0 and its comparison results are fictional worked examples.

Pupils must record their own P1 observations, including operator errors, without copying invented successes. Judge both the output and its reason.

Routine coverage is deliberately limited; boundary and variation tests follow next week.

By the end, I can test routine cases against expectations and count full passes honestly.

  • Use the supplied scenario, student illustrations and blank paper. For numeric work, offer counters or a calculator after learners show the setup. Fictional records are supplied; personal data and paid accounts are unnecessary.

  • The saved P1 version 1 cards, catalogue B version 1 and manual checklist from Week 32

  • Paper test sheets with case ID, input, purpose, expected result, observed result, judgement and trace reference

  • A folder for all versions and results; keep any reserved final evaluation cases separate from development work

Main lesson · Section 2

Teach fixed-version tests with full-pass criteria

Distinguish supplied Q0 records from learners’ actual P1 runs and from the pouch example.

Read the shared activity contract and methods

This week you will turn separate paper traces into a test record. Choose several ordinary requests, write the required answers first, then run the same saved prototype on every request.

Testing is useful when it can reveal a mistake, so keep failures as carefully as successes. A demonstration chosen because it works is not a complete evaluation.

Use catalogue B version 1 in order: B1 Bookmark drawing, 10 minutes, quiet Yes; B2 Story circle, 8 minutes, quiet No; B3 Pattern puzzle, 12 minutes, quiet Yes; B4 Tower challenge, 15 minutes, quiet No.

These fictional values assume materials are available. Inputs are whole minutes from 0 to 30 and Quiet required Yes or No. Time must fit AND either quiet is not required or the activity is quiet. No allows either kind.

Select the first fit with a correct reason; otherwise report no match. Missing or invalid input requires clarification. No booking or publishing takes place.

Keep the P1 version 1 instructions from Week 32: validate and stop with clarification if input is invalid; otherwise start at B1, check both conditions, suggest the first passing row and stop.

After a failure advance one row; report no match only after all rows fail. Reset to validation and B1 for each new valid request. The manual baseline marks every row against both conditions and selects the first fit.

Both methods must follow the same contract.

Prepare criteria and the four routine cases

Give each case an ID. Record its exact input, purpose, expected output and expected explanation before running it. Then add observed output, observed explanation, pass or fail, and a trace reference.

Put the prototype version, catalogue version and baseline method at the top of the sheet.

A pass needs the correct result and a reason supported by the checked conditions; the right activity with a false reason is not a full pass.

Our routine set R contains four valid requests. R1 is 11 minutes Yes, checking an early quiet match. R2 is 9 minutes No, checking that the search reaches a later fitting row.

R3 is 6 minutes No, checking that a valid request can exhaust the list. R4 is 9 minutes Yes, checking that a time fit alone is insufficient. These cases do not cover every accepted input or validation error.

CORE IDEA Repeated success on ordinary cases is necessary but not sufficient.

UNDER THE HOOD A test case includes input, setup, expected behavior, actual behavior, and result. Precommitting expectations reduces hindsight bias.

Repeated normal tests establish basic reliability but say little about uncommon conditions.

MODEL REASONING Write the expected output first, keep the prototype version fixed, record every actual output, and count passes without deleting failures.

Selected case: Independently audit this fictional equipment selector. Catalogue E has E1 first with capacity 4 and E2 second with capacity 8. Valid group sizes are whole numbers 1 to 10.

Select the first item with capacity at least the group size, or no match; invalid input needs clarification.

Write all expected results, mark full passes, calculate the fraction and explain the failure. Give one untested input category. No booking occurs.

Expected group 3: E1 because 4 holds 3. Group 6: E2 because E1 is too small and 8 holds 6. Group 9: no match because both capacities are too small.

The first and third pass; the second fails both output and reason, giving 2 of 3 full passes. The record suggests a capacity-check problem but the saved instructions and trace are needed to locate it.

Missing, nonwhole or out-of-range input is untested, as is equality with a capacity.
