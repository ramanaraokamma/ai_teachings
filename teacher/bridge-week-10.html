A fictional cupboard record has a name, capacity and used count. A list asks us to remember positions. Named fields make the intended meaning visible.

Our schema requires name as text and capacity and used as nonnegative integers, with used no greater than capacity.

Square brackets look up the value for a key. The quoted key "used" is text; its value is an integer. Assigning to an existing key replaces that field. Other fields remain the same.

Dictionary syntax does not enforce our schema: the programmer must check it.

Schemaname text, capacity/used nonnegative integers and used<=capacity. Example arithmetic does not enforce it.

Model complete Red practice

record = {"name": "Red", "capacity": 9, "used": 2}
def remaining(capacity, used):
    return capacity - used

record["used"] = 9
print(remaining(record["capacity"], record["used"]))
print(record["capacity"])

Read the shelf zero/missing example

A zero field is still present. A dictionary record describes a shelf. The program distinguishes missing data from an actual zero.

Python 3: shelf={"count":0,"name":"Atlas"}; print(shelf["count"]); print(shelf.get("price")); print("count" in shelf).

For the pictured shelf, count is present with 0 and price is absent. get without a default returns None for absence, while membership checks whether the key exists. A present key can also explicitly hold None: get then gives None but membership is True. Do not call get alone a presence test.

The selected describe function uses its own narrow policy that absent/None count is unavailable and returns the label missing; supplied numeric 0 must remain a value. It does not validate arbitrary record types or all possible counts.

Trace lookup and membership

Dictionary keys name fields. Presence is different from truthiness of a value; a measured zero should not be discarded as if the field were absent.

shelf = {"count": 0, "name": "Atlas"}
print(shelf["count"])
print(shelf.get("price"))
print("count" in shelf)

Predict added zero price

Change: Add the field price with value 0.

Prediction: The price lookup now returns 0 instead of None.

Reason: A recorded zero is a present value, whereas the earlier lookup had no field.

State explicit None policy limits

None is also a possible explicitly stored value; real record contracts must define how missing and null values are represented.

Diagnose misconceptions

A successful run proves the conclusion: Named fields reduce position mistakes but do not prove that a record is accurate. A capacity of 2 with used of 5 is representable in a dictionary and violates this schema.

Matching the example is enough: Require the new W4 case, explicit predictions and an explanation. Fresh retry: create a Gold record with capacity 11 and used 3; return 8, update used to 11 and return 0.

Require field lookups rather than copied literal arguments.

A convenient shortcut preserves meaning: cupboard["Used"] raises KeyError here because keys are case sensitive. Correct it to "used".

Adding a new field called "Used" would create a second key and leave the original unchanged; it would not repair the intended lookup.

def describe(record):
    count = record.get("count")
    if count is None:
        return "missing"
    return count

print(describe(record))
