Learning goal and precision

Primary target: Compare expected and observed traces to locate the first difference

Use debugging as evidence-based investigation of a stated procedure. Distinguish finding the first observed divergence from establishing a unique root cause.

The arithmetic examples show that two faults can fit one result and that a test may separate two explanations while still missing a different fault. Use paper traces and preserve the original failing case throughout repair.

By the end, I can choose a test that separates two possible causes of an error.

Main lesson · Section 2

Teach debugging as a testable comparison

Preserve the specification, expected trace and actual record before selecting a repair.

Begin with the points-machine divergence

A paper points machine must add 3 to its starting score, double the updated score, then subtract 2 and report. From 4 the expected values are 4, 7, 14 and 12. These instructions are the specification.

Calculate the expected result from them before looking at the machine output.

An observed run instead records 4, 7, 11 and 9. The final result is wrong, but changing the report from 9 to 12 would only hide this particular failure.

Compare the intermediate values to find where the behaviour first stopped matching the instructions.

The first difference is after the doubling instruction: expected 14, observed 11. The final subtraction is consistent with the observed 11, since 11 minus 2 is 9.

That later difference can be a consequence of the earlier fault rather than a second faulty subtraction. A trace narrows the investigation; it does not automatically reveal every cause.

Define a reproducible record and stable expectation

Record the input, the exact instruction version, expected values, observed values and first mismatch.

This makes the failure reproducible: someone else can follow the same procedure with the same starting value and check your observation.

Do not rewrite the expected column to match the observed result. If the specification itself seems ambiguous, clarify it first and record that change openly.

A test can judge an implementation only against a stated expectation.

Model the add-6 versus double comparison

A fictional paper calculator should double the current value, but a copied instruction behaves strangely.

After input 6, the faulty step reports 12. Hypothesis A: add 6. Hypothesis B: double.

Both hypotheses fit this first observation. A new input may be chosen.

Repeating input 6 would not separate the two hypotheses because both again predict 12. Input 2 makes their predictions different before the test is run.

The second record supports investigating an added constant, but inspecting the instruction is still needed to confirm the implementation.

Repeat an input that cannot distinguish the hypotheses

  1. Change: Use input 6 again instead of 2.

  2. Prediction: Both hypotheses predict 12; the test remains inconclusive.

  3. Reason: A revealing test requires different predicted outputs, not merely another recorded run.

Limit the diagnosis to the proposed alternatives

Two toy hypotheses do not exhaust every possible bug; a matching output alone cannot identify arbitrary hidden code.

Extend to competing faults in the full procedure

For the faulty doubling step, two explanations fit the observed change from 7 to 11. Perhaps the step adds 4. Perhaps it adds the original starting score, which was 4.

Repeating the same start 4 cannot separate those explanations because they make the same prediction.

Start scoreExpected final resultIf step adds 4 or original start
4129 under either explanation
287 if add 4 or 5 if add original 2
51410 if add 4 or 11 if add original 5

Starting at 2 produces 5 after the first addition. The intended double gives 10 and then reports 8. Adding 4 would give 9 and report 7. Adding the original 2 would give 7 and report 5.

The different predictions make this a revealing test.

If the observed final result is 7, it supports add 4 over add original among these two explanations. Other faults could still give 7, so inspect the actual instruction or more checkpoints before claiming a unique cause.

CORE IDEA Debugging finds the broken assumption or step before changing the solution.

UNDER THE HOOD Debugging is causal diagnosis. The first observable divergence narrows the faulty assumption, data, state, condition, or step.

Changing multiple things at once destroys evidence about which change repaired the behavior.

Draw a fresh example with all three stages:

Every step connects a claim to observable evidence.

CASE A paper robot hits a wall because one turn instruction assumes it faces north when it actually faces east.

STEP 1 — OBSERVE expected path and actual trace

STEP 2 — TRACE locate the first difference and test one cause

STEP 3 — CONCLUDE targeted correction plus repeated test

MODEL REASONING Trace expected and actual positions step by step. The first mismatch reveals the earliest plausible cause.

Change that instruction or assumption only, then rerun the identical maze to show whether the cause was correct.

DO NOT OVERCLAIM A successful new run does not prove the diagnosis if several things changed together.

W1 Locate the first difference

A procedure must add 2, double the updated value, then subtract 1. Starting at 3, an observed trace is 3, 5, 8, 7.

Write the expected trace, identify the first difference and explain why the final subtraction is not necessarily a separate fault.

Expected trace: 3, 5, 10, 9. First difference is the doubling checkpoint: 10 expected versus 8 observed. The later 8 minus 1 equals 7, so the observed subtraction is consistent with its input.

Investigate the earlier step before claiming another fault.

W2 Choose between two explanations

In W1 the faulty middle step may add 3, or add the original starting value. Both explain 5 becoming 8 when the start is 3. Choose start 1 or start 3 for a revealing new test.

Predict the final result under each explanation and under the intended procedure.

Choose start 1. After add 2 the value is 3. Adding 3 then subtracting 1 reports 5; adding original 1 then subtracting 1 reports 3. Doubling then subtracting 1 should report 5.

This separates the two fault explanations, but a final 5 alone cannot separate add 3 from correct doubling on this input; retain the original failing start 3.

W3 Reject a repair that hides the symptom

A learner repairs the original points machine by reporting 12 for every input, because 12 is correct from start 4. Give a different starting input and its expected output under add 3, double, subtract 2.

Explain why the constant report is not a valid repair and what earlier evidence should be preserved.

Start 2 should report 8, with trace 2, 5, 10, 8; other correctly calculated starts with a different output also work. Always reporting 12 breaks the specification.

Preserve the original input and observed intermediate trace as evidence, then correct the faulty instruction and rerun the cases.

W5 Make a defensible completion claim

After repairing W4, all three chosen tests pass. Write a short report with the fault, the exact repair, the three inputs and expected outputs, and what those passing tests establish.

Explain why saying every possible error is now impossible would go beyond the evidence.

The copied rule excluded equality. Change above 5 to at least 5 after the add 1 step. Tests 3, 4 and 5 now report Single, Group and Group.

The repair passes these checks around this boundary and retains the tested neighbouring behaviour. Other inputs, missing values or unrelated implementation faults were not established by these three tests.
