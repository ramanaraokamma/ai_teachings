Explain the mechanism

Explain the mechanism

Follow the information instead of imagining magic inside the machine.

INPUT expected path and actual trace

PROCESS locate the first difference and test one cause

OUTPUT targeted correction plus repeated test

CORE IDEA Debugging finds the broken assumption or step before changing the solution.

UNDER THE HOOD Debugging is causal diagnosis. The first observable divergence narrows the faulty assumption, data, state, condition, or step. Changing multiple things at once destroys evidence about which change repaired the behavior.

Draw a fresh example with all three stages:

Every step connects a claim to observable evidence.

CASE A paper robot hits a wall because one turn instruction assumes it faces north when it actually faces east.

STEP 1 — OBSERVE expected path and actual trace

STEP 2 — TRACE locate the first difference and test one cause

STEP 3 — CONCLUDE targeted correction plus repeated test

MODEL REASONING Trace expected and actual positions step by step. The first mismatch reveals the earliest plausible cause. Change that instruction or assumption only, then rerun the identical maze to show whether the cause was correct.

DO NOT OVERCLAIM A successful new run does not prove the diagnosis if several things changed together.

What new evidence could change this answer?

Concrete teaching case

A robot should go from square one to square three. Its program is MOVE ONE, STOP.

Find the cause and repair one thing.

Exact explanation to model

It stops at square two because one move is missing. Add MOVE ONE before STOP and retest from the same start.

Explain the added worked example

A paper points machine must add 3 to its starting score, double the updated score, then subtract 2 and report. From 4 the expected values are 4, 7, 14 and 12. These instructions are the specification. Calculate the expected result from them before looking at the machine output.

An observed run instead records 4, 7, 11 and 9. The final result is wrong, but changing the report from 9 to 12 would only hide this particular failure. Compare the intermediate values to find where the behaviour first stopped matching the instructions.

The first difference is after the doubling instruction: expected 14, observed 11. The final subtraction is consistent with the observed 11, since 11 minus 2 is 9. That later difference can be a consequence of the earlier fault rather than a second faulty subtraction. A trace narrows the investigation; it does not automatically reveal every cause.

Record the input, the exact instruction version, expected values, observed values and first mismatch. This makes the failure reproducible: someone else can follow the same procedure with the same starting value and check your observation.

Do not rewrite the expected column to match the observed result. If the specification itself seems ambiguous, clarify it first and record that change openly. A test can judge an implementation only against a stated expectation.

Key terms

TermMeaning
SpecificationA statement of what a system is required to do
Expected resultThe result worked out from the specification before running a test
Observed resultThe result actually recorded during a test
First divergenceThe earliest step where observed behaviour differs from expected behaviour
Regression testA repeated check that previously correct behaviour still works after a change

Model the reasoning aloud

Use the complete worked example below before asking learners to complete W2. Reveal a small part, invite a prediction, then explain the deciding step. These teacher notes contain solutions; do not reveal the independent case answer during modelling.

For the faulty doubling step, two explanations fit the observed change from 7 to 11. Perhaps the step adds 4. Perhaps it adds the original starting score, which was 4. Repeating the same start 4 cannot separate those explanations because they make the same prediction.

4129 under either explanation
287 if add 4 or 5 if add original 2
51410 if add 4 or 11 if add original 5

Starting at 2 produces 5 after the first addition. The intended double gives 10 and then reports 8. Adding 4 would give 9 and report 7. Adding the original 2 would give 7 and report 5. The different predictions make this a revealing test.

If the observed final result is 7, it supports add 4 over add original among these two explanations. Other faults could still give 7, so inspect the actual instruction or more checkpoints before claiming a unique cause.

A pictorial worked case: Debug the Cause

A fictional paper calculator should double the current value, but a copied instruction behaves strangely.

The facts we will use

After input 6, the faulty step reports 12. Hypothesis A: add 6. Hypothesis B: double.

Both hypotheses fit this first observation. A new input may be chosen.

Why this result follows

Repeating input 6 would not separate the two hypotheses because both again predict 12. Input 2 makes their predictions different before the test is run. The second record supports investigating an added constant, but inspecting the instruction is still needed to confirm the implementation.

What this example does not establish

Two toy hypotheses do not exhaust every possible bug; a matching output alone cannot identify arbitrary hidden code.

Change one thing in the pictured case

Change: Use input 6 again instead of 2.

Prediction: Both hypotheses predict 12; the test remains inconclusive.

Reason: A revealing test requires different predicted outputs, not merely another recorded run.

Ask while showing the picture

Cover the result. Ask learners to name the inputs and predict the next step. Uncover one step, connect the icon to the actual procedure, and explain its evidence. Then change the supplied condition and compare. The picture is a representation; it does not document execution of a real AI model.

Demonstrate and guide practice

Demonstrate and guide practice

Board sequence

Write the given facts: A robot should go from square one to square three. Its program is MOVE ONE, STOP.

Write the question to explain: Find the cause and repair one thing.

Reveal after predictions: It stops at square two because one move is missing. Add MOVE ONE before STOP and retest from the same start.

Keep for an independent attempt: A sorting rule says blue goes left. A blue card goes right. The reader correctly reports blue, but the direction rule says blue goes right. Which part should you fix first?

Classroom dialogue

Ask: Which facts are given, and which would we have to assume? Learners mark relevant details before discussing answers.

Say: Predict first. Show the rule, information path or calculation that would produce the result. A correct guess is not yet an explanation.

Reveal reasoning one step at a time. Explain why a tempting alternative fails. Write units and denominators for arithmetic, trace conditions for decisions, and identify supporting sources for claims.

In pairs, one learner solves while the other checks evidence; exchange roles. Remove the worked answer before independent assessment.

Model these guided questions

Add 4 fits both reported results: from 4, 7 plus 4 minus 2 is 9; from 2, 5 plus 4 minus 2 is 7. Adding the original start predicts 5 on the second run and is inconsistent. Inspect the actual middle instruction. If it says add 4, restore double the current score and expect 12 from start 4 and 8 from start 2; also check start 5 gives 14. This distinguishes the proposed faults without claiming no other cause exists. Exit: start 7. Below 7 runs zero times and reports 7; at most 7 adds 2 once and reports 9.

Diagnose and reteach

CLAIM TO REPAIR Changing every part is the best way to find a cause.

For guessing, return to given facts and request a trace. For vocabulary without application, use one example and one non-example. For arithmetic errors, check the setup before the calculation. Finish with a different uncoached case before recording mastery.

Address these additional misconceptions

The last wrong number locates the fault: Compare every aligned checkpoint; an early mismatch can cause several later wrong values.

One revealing test proves the only possible cause: List the explanations actually compared. A different, untested fault may make the same prediction.

A correct answer on one input proves the repair: Use the constant-report example and rerun original failing and previously passing cases.

Expected results should follow observed results: Calculate expectations from the specification first. Clarify genuine specification changes explicitly rather than hiding a failure.

Feedback

Explanations for the additional workbook examples

W1 Locate the first difference

A procedure must add 2, double the updated value, then subtract 1. Starting at 3, an observed trace is 3, 5, 8, 7. Write the expected trace, identify the first difference and explain why the final subtraction is not necessarily a separate fault.

Expected trace: 3, 5, 10, 9. First difference is the doubling checkpoint: 10 expected versus 8 observed. The later 8 minus 1 equals 7, so the observed subtraction is consistent with its input. Investigate the earlier step before claiming another fault.

W2 Choose between two explanations

In W1 the faulty middle step may add 3, or add the original starting value. Both explain 5 becoming 8 when the start is 3. Choose start 1 or start 3 for a revealing new test. Predict the final result under each explanation and under the intended procedure.

Choose start 1. After add 2 the value is 3. Adding 3 then subtracting 1 reports 5; adding original 1 then subtracting 1 reports 3. Doubling then subtracting 1 should report 5. This separates the two fault explanations, but a final 5 alone cannot separate add 3 from correct doubling on this input; retain the original failing start 3.

W3 Reject a repair that hides the symptom

A learner repairs the original points machine by reporting 12 for every input, because 12 is correct from start 4. Give a different starting input and its expected output under add 3, double, subtract 2. Explain why the constant report is not a valid repair and what earlier evidence should be preserved.

Start 2 should report 8, with trace 2, 5, 10, 8; other correctly calculated starts with a different output also work. Always reporting 12 breaks the specification. Preserve the original input and observed intermediate trace as evidence, then correct the faulty instruction and rerun the cases.

W4 Debug a new ticket rule

A paper ticket rule must add 1 to the input count. If the updated count is at least 5, report Group; otherwise report Single. A copied version says above 5. Choose the smallest three consecutive nonnegative starting counts that test just below, exactly at and just above the comparison boundary. Predict both versions, identify the revealing start and state the repair and retests.

Use starts 3, 4 and 5, which reach 4, 5 and 6. Intended results are Single, Group, Group. Copied results are Single, Single, Group. Start 4 exposes the equality fault. Restore at least 5 and rerun all three, retaining starts 3 and 5 as previously passing regression cases.

W5 Make a defensible completion claim

After repairing W4, all three chosen tests pass. Write a short report with the fault, the exact repair, the three inputs and expected outputs, and what those passing tests establish. Explain why saying every possible error is now impossible would go beyond the evidence.

The copied rule excluded equality. Change above 5 to at least 5 after the add 1 step. Tests 3, 4 and 5 now report Single, Group and Group. The repair passes these checks around this boundary and retains the tested neighbouring behaviour. Other inputs, missing values or unrelated implementation faults were not established by these three tests.

DimensionEvidence required
ExplanationNames the applicable idea or procedure and ties it to the supplied facts.
Trace and resultPreserves the given inputs and shows the relevant intermediate steps; distinguishes a prediction from an observed execution.

Record each dimension as not yet, with support, or independent. Accept a valid alternative procedure with a defensible trace. Do not penalise an honestly recorded model failure if the learner correctly explains its evidence and limits.

Feedback that the learner uses

Name the earliest unsupported step and give one action to repair it. Have the learner make that repair now and explain why. Then assess the relevant skill on a fresh, fully specified case. Confirm it was not previously practised with feedback; solve and check the new case before assigning it. A follow-up design prompt is a starting brief, not automatically an equivalent test.

Connect and extend learning

When the sorter fails, log the first wrong stage and change only the responsible rule, input, or label.

Use feedback, labs and repair paths

Use the two formative questions as supported practice, not as independent mastery scores. Discuss the deciding evidence rather than accepting a guessed selection.

The feedback comes from the reviewed public worked case. Do not reveal the separately reserved independent teacher answer until the learner has attempted that case.

Ask students to predict before running code. Preserve errors and actual outputs; collect a changed test and an explanation. The branch-boundary and indexing lessons deliberately include failure cases.

Use the earlier worked-explanation links to address a specific missing building block, then return to the current question. Adapt this suggestion after observing the learner; it is not an automatic diagnosis.

Collect the completed-work portfolio as evidence. Record support separately from correctness, and assess explanation, trace/test and limitations. Progress ticks and quiz selections alone do not establish mastery.
