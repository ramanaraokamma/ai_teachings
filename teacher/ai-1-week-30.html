Explain the mechanism

Follow the information instead of imagining magic inside the machine.

PROCESS candidate decision process

CORE IDEA A useful design makes required information and promised result explicit.

UNDER THE HOOD Interface contracts define inputs, outputs, types, allowed values, missing-data behavior, and guarantees. Good design avoids collecting data that cannot improve the promised result and avoids promising outcomes the process cannot support.

Draw a fresh example with all three stages:

Every step connects a claim to observable evidence.

CASE A sorter can use item type and location found to suggest a bin without collecting a student's name or face.

STEP 1 — OBSERVE minimal required information

STEP 2 — TRACE candidate decision process

STEP 3 — CONCLUDE specific promised result and uncertainty path

MODEL REASONING Prefer the design that meets the measurable need with fewer, clearer inputs and an honest output. State how missing values and ambiguous cases are handled before building.

DO NOT OVERCLAIM Every collected field creates cost and risk; every promised output needs evidence.

Concrete teaching case

A sorter suggests paper or plastic trays using material observations.

Name an input, output and unnecessary input.

Exact explanation to model

Input: material or a suitable image. Output: tray suggestion. Home address is unnecessary. Uncertain material needs review.

Explain the added worked example

Last week we identified a difficulty: some fictional activity choices did not fit the available time or room conditions. Now define the task precisely enough that two reviewers can agree whether an output is correct. A requirement such as “suggest a good activity” is too vague. State which inputs are accepted, what counts as compatible and what to do when no option fits.

For this paper project, a valid request contains an available time from 0 to 30 whole minutes and a quiet-room requirement written Yes or No. Yes means the activity must be marked quiet. No means either quiet or non-quiet activities are permitted; it does not mean noise is required. A missing or invalid value needs clarification, not a guessed value or a no-match claim.

A compatible activity takes no more than the available minutes and meets the quiet-room condition. If several activities fit, suggest the first in catalogue order. If none fits a valid request, report no match. Give a brief reason. This is a suggestion only: it does not book resources, tell anyone to begin or guarantee enjoyment.

These four rows are the complete approved catalogue for the paper model. Treat their times as fixed task values, not measured guarantees about real pupils. All required materials are assumed available. The catalogue order B1, B2, B3, B4 is the tie rule; it is not a claim that B1 is everyone’s favourite.

For 10 minutes with quiet required, B1 fits because 10 is no more than 10 and B1 is quiet. B2 fails the quiet requirement. B3 and B4 take too long. For 8 minutes with quiet not required, B2 fits; B1 takes too long. A request for 7 minutes has no compatible activity in this catalogue, even when quiet is not required.

Check each condition. A fast activity can still fail the quiet requirement. A quiet activity can still take too long. Exact equality is allowed: an activity listed as 10 minutes fits 10 available minutes. A blank time is different from a valid time of zero.

Model the reasoning aloud

Use the complete worked example below before asking learners to complete W2. Reveal a small part, invite a prediction, then explain the deciding step. These teacher notes contain solutions; do not reveal the independent case answer during modelling.

Write the request at the top of a sheet. If it is invalid, record what needs clarification and stop. Otherwise mark each catalogue row as compatible or incompatible using both conditions. Circle the first compatible row in order, or write no match if every row fails. Record the output and its reason. This checklist is our baseline.

The baseline can be correct on all cases when applied carefully. A prototype that matches it has not demonstrated better compatibility. It may still be easier to use or faster to trace, but those are separate claims that need their own measures. Do not make the baseline skip a condition just to make the prototype look better.

A pictorial worked case: Choose Inputs and Outputs

A fictional classroom chooses a storage bin for model parts.

The facts we will use

Catalogue order: B1 capacity 5, B2 capacity 9. Valid request is a whole part count 1–12.

Return first bin with capacity at least the count; none if neither fits; clarify invalid input.

Why this result follows

The baseline is an ordered catalogue scan, not a preference ranking. It makes expectations testable before a prototype is built. Count 10 is valid but has no matching bin; that differs from a blank count, which fails the input contract. Both situations need explicit output behavior.

What this example does not establish

Bin capacity is the only supplied fitting criterion; weight or shape suitability cannot be inferred.

Change one thing in the pictured case

Change: Change request 6 to 5.

Prediction: The baseline returns B1.

Reason: Its capacity equals the request, and at least includes equality.

Ask while showing the picture

Cover the result. Ask learners to name the inputs and predict the next step. Uncover one step, connect the icon to the actual procedure, and explain its evidence. Then change the supplied condition and compare. The picture is a representation; it does not document execution of a real AI model.

Demonstrate and guide practice

Demonstrate and guide practice

Board sequence

Write the given facts: A sorter suggests paper or plastic trays using material observations.

Write the question to explain: Name an input, output and unnecessary input.

Reveal after predictions: Input: material or a suitable image. Output: tray suggestion. Home address is unnecessary. Uncertain material needs review.

Keep for an independent attempt: A paper sorter must suggest pencil tray or book shelf. Choose one needed input and state the output. What should happen if the picture is blocked?

Classroom dialogue

Ask: Which facts are given, and which would we have to assume? Learners mark relevant details before discussing answers.

Say: Predict first. Show the rule, information path or calculation that would produce the result. A correct guess is not yet an explanation.

Reveal reasoning one step at a time. Explain why a tempting alternative fails. Write units and denominators for arithmetic, trace conditions for decisions, and identify supporting sources for claims.

In pairs, one learner solves while the other checks evidence; exchange roles. Remove the worked answer before independent assessment.

Model these guided questions

12 Yes: B1 and B3 fit; B2 and B4 are non-quiet, and B4 is also too long. Choose B1 because it is first in catalogue order. 8 Yes: B1 and B3 are too long; B2 is not quiet; B4 fails both. Report no match. Blank time requires clarification, not a guessed number. Exit: equal successful outputs on five cases do not show better accuracy for the app. A separate claim such as faster completion needs recorded times under comparable conditions, with errors and help also recorded.

Reduce help deliberately

Completion task: Using the catalogue, record the baseline output and reason for 10 minutes with quiet required, 8 minutes with quiet not required, and 7 minutes with quiet not required. Identify which no-match result is justified and why.

Teacher check: 10 Yes gives B1: 10 fits exactly and it is quiet. 8 No gives B2: B1 is too long, B2 fits and non-quiet is permitted. 7 No gives no match: even the shortest activity requires 8 minutes. That no-match result is justified by the complete catalogue.

Start by identifying the given inputs together. Leave the intermediate steps blank. If needed, model one step, then withdraw that help on the next step. Move to a full trace only when the partial trace is understood. For partners, alternate explainer and checker; collect a response from every learner before discussion.

Individual reasoning check

Use the worked case for Requirements and a simple baseline. Proposed explanation: “Quiet required No excludes quiet activities”. Decide whether this explanation is supported. Point to the step or supplied fact that decides; explain your repair if needed.

Expected correction: No removes the quiet restriction; it does not reverse it.

Collect explanations, not only yes/no votes. If a misunderstanding is common, re-model the relevant step for the class. If it affects a few learners, give a short targeted group explanation while others solve a more demanding variation.

Pictorial practice question

Trace requests 10 and blank. Why should they not receive the same explanation?

Reasoned teacher answer

10 is valid but neither bin fits: no match. Blank is missing input: request clarification before searching.

Changed-case reasoning: The baseline returns B1. Its capacity equals the request, and at least includes equality.

Collect each learner’s explanation before discussion. Use the first missing connection between input, deciding step and result to choose support. This question is worked-case practice, not fresh mastery evidence.

Make the lab runnable

Use the concrete case as the shared normal case and the independent question as a second case. Each pair creates a boundary or missing-information case and predicts its result before testing. Keep the expected result separate from an observed mistake.

Diagnose and reteach

CLAIM TO REPAIR A system can safely infer every missing input.

For guessing, return to given facts and request a trace. For vocabulary without application, use one example and one non-example. For arithmetic errors, check the setup before the calculation. Finish with a different uncoached case before recording mastery.

Address these additional misconceptions

Quiet required No excludes quiet activities: No removes the quiet restriction; it does not reverse it.

Ten minutes does not fit a ten-minute limit: No more than includes equality.

Blank time means zero: Blank is missing; zero is a valid input with no matching activity here.

A baseline must be bad to make a comparison useful: Use a credible simple method and accept a tie or a baseline win.

Explanations for the additional workbook examples

W1 Make a requirement checkable

Replace “suggest a good activity” with the time condition, quiet condition and tie rule used in this project. Explain why Quiet required No permits B1 as well as non-quiet activities when their times fit.

Time required must be no more than available time; when quiet is required the activity must be quiet. Choose the first compatible activity in B1 to B4 order. No means quiet is not required, not forbidden, so quiet B1 is permitted if 10 minutes fits.

W2 Run the baseline on three requests

Using the catalogue, record the baseline output and reason for 10 minutes with quiet required, 8 minutes with quiet not required, and 7 minutes with quiet not required. Identify which no-match result is justified and why.

10 Yes gives B1: 10 fits exactly and it is quiet. 8 No gives B2: B1 is too long, B2 fits and non-quiet is permitted. 7 No gives no match: even the shortest activity requires 8 minutes. That no-match result is justified by the complete catalogue.

W3 Separate invalid input from no matching option

Compare a request with blank minutes and Quiet required Yes to a request with 0 minutes and Quiet required Yes. What should the baseline record for each? Explain why these are different outcomes even though neither produces an activity suggestion.

Blank minutes is invalid and requires clarification of the missing time. Zero is a valid whole number within 0 to 30; no activity takes 0 minutes or less, so no match is justified. The first lacks a usable input; the second has a usable input but no compatible option.

W4 Build a baseline for a different catalogue

A paper room recommender uses R1 first, capacity 6, quiet Yes; then R2, capacity 10, quiet No. Valid requests give a whole group size from 1 to 12 and Quiet required Yes or No. A room fits when capacity is at least group size and the quiet condition is met; choose the first fitting room. Record outputs and reasons for 6 people Yes, 8 people No and 8 people Yes. Explain how a manual baseline can be compared fairly with a prototype. No real booking is allowed.

6 Yes gives R1: equality fits and it is quiet. 8 No gives R2: R1 is too small and R2 meets capacity with quiet not required. 8 Yes gives no match: R1 is too small, R2 is not quiet. Use the same room catalogue, request set and requirements for both methods and keep all results. Compare suggestions only; do not make bookings.

W5 Challenge an unfair comparison

Team A tests a prototype on five easy requests and the manual baseline on five different requests, then reports only the prototype’s successful outputs. Identify two changes needed for a fair comparison. If both methods then meet all requirements, what can and cannot be concluded about compatibility?

Use the same requests and catalogue for both with the same judging rules, and retain all outputs including failures and no-match or clarification results. If both meet the requirements on those cases, both pass those checks; the results do not demonstrate the prototype has better compatibility or prove either works on every possible case.

DimensionEvidence required
ExplanationNames the applicable idea or procedure and ties it to the supplied facts.
Trace and resultPreserves the given inputs and shows the relevant intermediate steps; distinguishes a prediction from an observed execution.

Record each dimension as not yet, with support, or independent. Accept a valid alternative procedure with a defensible trace. Do not penalise an honestly recorded model failure if the learner correctly explains its evidence and limits.

Feedback that the learner uses

Name the earliest unsupported step and give one action to repair it. Have the learner make that repair now and explain why. Then assess the relevant skill on a fresh, fully specified case. Confirm it was not previously practised with feedback; solve and check the new case before assigning it. A follow-up design prompt is a starting brief, not automatically an equivalent test.

Support and stretch

Exit reflection
