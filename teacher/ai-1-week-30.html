Main lesson · Section 2

Teach the complete contract before a fair baseline comparison

Provide the full activity catalogue and distinguish it from the two-bin worked case.

Define the activity contract

Last week we identified a difficulty: some fictional activity choices did not fit the available time or room conditions. Now define the task precisely enough that two reviewers can agree whether an output is correct.

A requirement such as “suggest a good activity” is too vague. State which inputs are accepted, what counts as compatible and what to do when no option fits.

For this paper project, a valid request contains an available time from 0 to 30 whole minutes and a quiet-room requirement written Yes or No. Yes means the activity must be marked quiet.

No means either quiet or non-quiet activities are permitted; it does not mean noise is required. A missing or invalid value needs clarification, not a guessed value or a no-match claim.

A compatible activity takes no more than the available minutes and meets the quiet-room condition. If several activities fit, suggest the first in catalogue order. If none fits a valid request, report no match.

Give a brief reason. This is a suggestion only: it does not book resources, tell anyone to begin or guarantee enjoyment.

Read the complete activity catalogue

Catalogue order and activityMinutes requiredQuiet activity
B1 Bookmark drawing10Yes
B2 Story circle8No
B3 Pattern puzzle12Yes
B4 Tower challenge15No

These four rows are the complete approved catalogue for the paper model. Treat their times as fixed task values, not measured guarantees about real pupils. All required materials are assumed available.

The catalogue order B1, B2, B3, B4 is the tie rule; it is not a claim that B1 is everyone’s favourite.

Model equality, conditions and missingness

For 10 minutes with quiet required, B1 fits because 10 is no more than 10 and B1 is quiet. B2 fails the quiet requirement. B3 and B4 take too long. For 8 minutes with quiet not required, B2 fits; B1 takes too long.

A request for 7 minutes has no compatible activity in this catalogue, even when quiet is not required.

Check each condition. A fast activity can still fail the quiet requirement. A quiet activity can still take too long. Exact equality is allowed: an activity listed as 10 minutes fits 10 available minutes.

A blank time is different from a valid time of zero.

Run and record the manual baseline

Write the request at the top of a sheet. If it is invalid, record what needs clarification and stop. Otherwise mark each catalogue row as compatible or incompatible using both conditions.

Circle the first compatible row in order, or write no match if every row fails. Record the output and its reason. This checklist is our baseline.

The baseline can be correct on all cases when applied carefully. A prototype that matches it has not demonstrated better compatibility.

It may still be easier to use or faster to trace, but those are separate claims that need their own measures. Do not make the baseline skip a condition just to make the prototype look better.

CORE IDEA A useful design makes required information and promised result explicit.

UNDER THE HOOD Interface contracts define inputs, outputs, types, allowed values, missing-data behavior, and guarantees.

Good design avoids collecting data that cannot improve the promised result and avoids promising outcomes the process cannot support.

W3 Separate invalid input from no matching option

Compare a request with blank minutes and Quiet required Yes to a request with 0 minutes and Quiet required Yes. What should the baseline record for each?

Explain why these are different outcomes even though neither produces an activity suggestion.

Blank minutes is invalid and requires clarification of the missing time. Zero is a valid whole number within 0 to 30; no activity takes 0 minutes or less, so no match is justified.

The first lacks a usable input; the second has a usable input but no compatible option.

W5 Challenge an unfair comparison

Team A tests a prototype on five easy requests and the manual baseline on five different requests, then reports only the prototype’s successful outputs. Identify two changes needed for a fair comparison.

If both methods then meet all requirements, what can and cannot be concluded about compatibility?

Use the same requests and catalogue for both with the same judging rules, and retain all outputs including failures and no-match or clarification results.

If both meet the requirements on those cases, both pass those checks; the results do not demonstrate the prototype has better compatibility or prove either works on every possible case.
